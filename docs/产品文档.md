## 1. 产品概述

RustGIS 是一款使用**纯 Rust** 开发的桌面地理信息系统（GIS），目标是在功能上复刻
ESRI ArcGIS（ArcMap / ArcGIS Pro）的核心能力体系：地图显示、数据管理、符号化与
制图、空间分析、地理处理、网络与 3D 分析等。

区别于商业 GIS 产品，RustGIS 把**低内存占用**和**高性能**作为第一产品指标，同时借助
Rust 语言特性保证运行时内存安全，并通过单一静态二进制实现跨平台分发。

## 2. 背景与动机

| 现状痛点（以 ArcGIS 为代表） | RustGIS 的应对 |
| --- | --- |
| 内存占用高：千万级要素桌面场景常驻内存常达 1~3 GB | 零拷贝数据管线 + 空间索引按需加载，目标 ≤ 300 MB |
| 启动与交互慢，重度依赖 .NET/MFC 运行时 | 纯 Rust 静态链接，冷启动 ≤ 3 s，无 GC 停顿 |
| 授权昂贵、闭源，二次开发受限制 | 开源（MIT / Apache-2.0 双协议），Rust crate 生态可扩展 |
| 崩溃后数据丢失风险（C++ 内存不安全） | Rust 所有权模型消除野指针/数据竞争类缺陷 |
| 渲染与分析单线程，难以吃满多核 | rayon 并行渲染与分析，性能随核心数线性扩展 |

## 3. 产品定位与核心价值

**定位**：面向专业用户的开源、轻量、高性能桌面 GIS 平台。

**核心价值**：

1. **低内存**：同等数据规模下内存占用显著低于商业 GIS（量化目标见 §8）。
2. **高性能**：渲染与分析全面并行化，目标较 ArcGIS 同场景快 5~10 倍。
3. **内存安全**：编译期消除整类内存缺陷，生产环境零野指针崩溃。
4. **跨平台**：Windows / Linux / macOS 单一代码库，单一静态可执行文件分发。
5. **开放可扩展**：模块化 crate 架构，预留插件与地理处理扩展机制。

## 4. 目标用户

- **GIS 工程师 / 测绘人员**：日常制图、数据编辑与分析；
- **规划与自然资源部门**：大比例尺底图与海量矢量数据管理；
- **电力、能源、交通行业**：网络分析、管线资产管理；
- **Rust 与 GIS 研发者**：以库（crate）形式集成空间计算能力。

## 6. 技术架构

### 6.1 技术选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| GUI 框架 | **eframe / egui 0.31** | 纯 Rust 即时模式 UI，无外部运行时依赖，内存开销极低 |
| 窗口系统 | winit（eframe 内置） | 跨平台原生窗口 |
| 渲染 | v0.2：egui CPU 渲染（矢量 → 三角网格缓存 + `egui::Mesh` 批绘制）；规划 **wgpu** GPU 管线 | 海量要素场景迁移至 GPU 批渲染 |
| 几何/空间 | 文件几何内核：`geo-types` 0.7；空间分析（v0.2.2 起）：**`geo` 0.33**（Buffer / BooleanOps / Earcut，纯 Rust、无 C 依赖）；规划 R-Tree 空间索引 | 早期规划的自研几何引擎已调整为「成熟 crate 打底 + 按需自研」：v0.2.2 的缓冲区、布尔融合与三角剖分全部委托 `geo`，产品文档 §12.3 记录分工与边界 |
| 并行 | rayon（规划） | 分析/渲染任务并行化 |
| 数据格式 | v0.2：GeoJSON（`geojson` 0.24）、Shapefile（`shapefile` 0.9 + `dbase`，GBK 等 DBF 编码自动检测）、**工程文件 .rustgis（版本化 JSON，`serde` 1 + `serde_json` 1，v0.3 起为 v5）**；v0.3：**栅格 GeoTIFF / BigTIFF（`tiff` 0.11，纯 Rust；无压缩 / LZW / Deflate / PackBits / Fax / ZSTD / WebP）**；v0.4：**Sentinel-2 SAFE 产品包（`quick-xml` 0.37 解析元数据 + `j2k` 0.12 纯 Rust 解码 JPEG 2000）**；规划：GeoPackage、File GDB（只读）、PostGIS、WMS/WMTS | 文件选择器 `rfd` 0.15；**导入与工程打开/保存全链路（文件对话框 + 序列化/解析 + 几何展开 + 三角剖分 + 栅格解析/统计/概览构建）均在后台线程执行，UI 线程只取回成品**，大文件不会锁死窗口 |
| 国际化 | `sys-locale` 检测系统区域设置 + 内置翻译表（简体中文 / English / 日本語） | 启动跟随系统语言，菜单内可手动切换 |
| 中文字体 | 编译期内嵌阿里巴巴普惠体 3.0（55 Regular，`resources/fonts/`） | egui 内置字体不含 CJK 字形，不加载会显示为方框；内嵌后无需依赖系统字体 |
| 语言版本 | Rust（edition 2024） | 稳定版工具链 |

│  ├─ rustgis-data      # 数据源接入：GeoJSON/Shapefile/GeoPackage/...
│  ├─ rustgis-render    # 渲染管线（瓦片缓存、LOD、符号化）

   ├─ menus.rs          # 10 个菜单的 key 驱动定义（i18n；「地理处理」= 缓冲区 + 叠加工具）
   ├─ dialog.rs         # 系统原生提示框 / 询问框（正在开发中 / 错误 / 关于 / 保存更改 / 金字塔概览）
   ├─ app/              # 应用层模块（mod.rs 为布局编排与工程状态机）
   │  ├─ buffer_dialog.rs     # 缓冲区参数窗口（独立顶层窗口）
   │  ├─ geoprocess_dialog.rs # 叠加工具参数窗口（裁剪/相交/联合/合并/融合，共用骨架）
   ├─ project.rs        # 工程文件（.rustgis）：版本化 JSON 读写（后台线程调用）
   ├─ i18n.rs           # 三语文案表（zh/en/ja）+ 占位符替换
   ├─ fonts.rs          # CJK 字体加载（编译期内嵌阿里巴巴普惠体）

   │  ├─ tri.rs         #   geo Earcut 三角剖分封装（外环 + 孔，导入时缓存）
   │  ├─ buffer.rs      #   缓冲区引擎（geo Buffer/BooleanOps + ArcGIS 参数语义）
   │  └─ overlay.rs     #   叠加分析引擎（裁剪/相交/联合/合并/融合 + 属性传递）
   ├─ raster/           # 栅格：GeoTIFF（v0.3）/ Sentinel-2 SAFE（v0.4）
   │  ├─ mod.rs         #   RasterDataset / 层级选择 / 窗口读取 / 显示设置 / 结构化错误
   │  ├─ tiff_file.rs   #   TIFF 解码（分块窗口读取 + LRU 块缓存 + 平面/交错）
   │  ├─ geotiff.rs     #   GeoTIFF 标签（仿射 / EPSG / GCP / GDAL 统计）
   │  ├─ safe.rs        #   SAFE 包解析（产品级别 / MTD_TL 地理编码 / 波段枚举）
   │  ├─ jp2.rs         #   JPEG 2000 读取（j2k 分量平面 + 区域/降采样解码）
   │  ├─ pyramid.rs     #   外部概览（.ovr，GDAL / ArcGIS 兼容）
   │  ├─ stats.rs       #   统计累加器（min/max/mean/std + 直方图 + 分位）
   │  └─ paint.rs       #   栅格绘制（选层 → 重采样 → 拉伸 → 纹理缓存）
   └─ map/              # 视图变换（中心+比例尺）、平移/缩放交互

> 已知边界：世界坐标按经纬度（度）处理，未做投影变换（缓冲区在「地理坐标系 +
> 线性单位」时按纬度做各向异性近似测地线，见 §12.3）；导入全程后台线程执行
> （选择 / 解析 / 三角剖分），但**渲染仍逐帧重建**（大图层平移缩放时帧耗与顶点数
> 成正比，见 §6.2 已知边界）。
>
> v0.2.1 进展：**投影 / 坐标系识别与展示**已实现（§12.2）——GeoJSON 按
> RFC 7946 默认 WGS 84（EPSG:4326），Shapefile 读同目录 `.prj`（WKT，识别
> EPSG 代码 / 投影模型 / 名称兜底）；工程文件升 v3 持久化工程默认投影 /
> 坐标系，状态栏实时显示。**仍不做坐标重投影**（混合坐标系图层的正确
> 套合属于 `rustgis-spatial` 的 proj 集成，见 §13）。

### 6.3 低内存设计策略

- **按需加载**：空间索引 + 瓦片式（tile）要素加载，仅驻留可视范围数据；
- **零拷贝**：文件解析产物（字节切片）直接映射至渲染对象，避免重复 clone；
- **小对象池化**：要素句柄用索引 + 驻留表，避免堆碎片；
- **显式内存上限**：缓存（瓦片、索引、符号）设置可配置上限与 LRU 淘汰。

**工程文件**（v0.2 新增，对标 ArcGIS 的 .aprx / .mxd）：

- **格式**：单个 `.rustgis` 文件（版本化 JSON，`version` 字段；高于当前应用支持的
  版本时拒绝加载并说明原因）。内容为**全部图层**（名称、显隐、渲染样式、
  点 / 线 / 多边形源几何——含孔及其与外环的归属分组）+ **地图视图**（中心 + 比例尺）。
  三角剖分结果不入库，打开时按导入路径同一套算法重建（保证渲染一致且文件更小）。
- **新建工程**：清空全部图层、视图重置为默认范围、工程名回"未命名"。
- **打开工程**：系统文件选择器（过滤 .rustgis）→ 后台线程解析 + 三角剖分 →
  整体替换图层并恢复保存时的视图（无视图则自动适配数据范围）。
- **保存 / 另存为**：有工程路径直接保存，否则走"另存为"（默认文件名
  `untitled.rustgis`，扩展名缺省时自动补全）；序列化在后台线程完成
  （大工程 JSON 可达 MB 级，UI 不阻塞）。
- **未保存更改拦截**（与 ArcGIS 一致）：图层增删 / 显隐 / 拖拽排序、以及
  平移 / 缩放 / 双击等视图变化都会把工程标记为"已修改"。此时
  **新建 / 打开 / 退出**（菜单「退出」或标题栏 X）先弹"保存更改？"三按钮提示：
  - **保存**：有路径直接保存、无路径先弹"另存为"，保存成功后继续原动作
    （新建 / 打开 / 退出）；
  - **不保存**：放弃更改直接执行原动作；
  - **取消**：什么都不做（若源于标题栏 X，则窗口保持打开）。
- **标题栏**：显示「工程名 — RustGIS 版本」（未保存过为"未命名"），
  对标 ArcGIS Pro 标题栏显示工程名。
- 全流程后台线程执行 + 50ms 定时唤醒（与导入流水线同款约定），状态栏同步
  「正在打开工程「x」… / 正在保存工程… / 已保存 / 已打开」；失败弹错误对话框。

**图层管理面板**（左侧，v0.2 新增）：图层树自顶向下排列（与 ArcGIS 一致），
每行只显示**图例符号 + 图层名**（面 = 填充块+边框、线 = 斜线段、点 = 圆点，
配色随图层样式；隐藏图层名称呈弱色）；**拖拽行即可调整叠放层级**（拖动中
列表保持不动、只显示落点指示，**松开鼠标时才真正移动**），**右键菜单**提供
显示/隐藏 与 删除（删除为红色警示项）；
面板底部为图层操作与地图交互提示；
导入全程在后台线程执行：文件对话框弹出期间主窗口不阻塞，选定文件后解析 / 几何展开
/ 三角剖分同样在后台进行，面板提示「正在等待文件选择…」/「正在解析数据…」并置灰
「添加」按钮，状态栏同步显示进度，导入完成后一次性加入图层并缩放至全图。

**地图视图交互**（v0.2 新增）：地图画布为**白色背景**（GIS 底图习惯）；
左键拖动平移、滚轮以光标为中心缩放、双击缩放至全图；空数据时显示引导文案。

**视觉主题**（v0.2.0 定型）：整应用采用**白底浅色主题**——窗口 / 面板 / 地图画布 /
工具对话框背景全为纯白，面板之间以 1px 发丝线分隔（不用色块对比），控件交互态
（悬停 / 按下 / 选中）与强调色统一走蓝色系（ArcGIS 蓝 `#0071BC`）。
全部设计 token（颜色 / 描边 / `Visuals`）收敛在 `src/style.rs`，换主题只改一处；
图层默认符号化配色（填充柔蓝、描边 ArcGIS 蓝、点橙红）同样按白底画布在该模块定义。

**提示类弹框走系统原生样式**（`src/dialog.rs`）：「功能开发中」/ 错误 / 关于 /
「是否构建金字塔」/「保存更改？」不再用 egui 自绘窗口，统一由 `rfd::MessageDialog`
（同文件选择器一套库）弹出**系统原生对话框**——Windows 为 ComCtl32 v6 TaskDialog、
macOS 为 NSAlert、Linux 为 GTK 对话框；图标、标题栏、字体与按钮外观跟随操作系统，
按钮文案仍随界面语言翻译（自定义按钮依赖 `build.rs` 嵌入的应用 manifest）。
对话框在后台线程弹出并阻塞该线程，UI 循环每帧非阻塞轮询结果，弹框开着时地图
照常平移缩放。

**启动体验**：Windows 下编译为 GUI 子系统程序（`#![windows_subsystem = "windows"]`），
启动时不出现控制台窗口，直接显示主窗体。

**多窗口**（v0.2.2 新增）：应用支持**多个真实系统窗口**——工具对话框（缓冲区分析，以及
叠加类的裁剪 / 相交 / 联合 / 合并 / 融合）
经 egui 多视口在独立顶层窗口中打开，与主窗口并存且互不阻塞；窗口内界面状态放在
`Arc<Mutex<…>>`，跨线程只传「消息」与字符串快照，不共享 `RustGisApp` 所有权。

状态栏显示三段信息：`状态 | 光标经纬度（鼠标悬停地图时）| 投影/坐标系/版本`。
第三段自 v0.2.1 起**动态反映工程默认投影 / 坐标系**（如 `投影: 投影坐标系 |
坐标系: EPSG:4549`；未设置时显示"未设置"），不再是硬编码的"未设置"。

后台栅格任务（统计 / 金字塔构建）**进行中**的进度仍显示在状态栏；**完成后改为在
窗口右下角弹出一条通知**（淡入、悬停冻结倒计时、6 秒后淡出，同时最多 4 条，
右上角可手动关闭），不再占用状态栏文字位。通知外观按工业软件惯例绘制：
卡片 + 1px 发丝边框 + 左侧状态色标 + 底部寿命进度条。

**多语言**：界面默认跟随系统区域设置（`zh`→简体中文、`ja`→日本語、`en`→English，
其他默认简体中文），并可在「帮助 → 语言」中随时切换（状态栏等已显示文案即时生效）。
所有 UI 文案以 i18n key 管理（`src/i18n.rs`），新增语言只需实现一个翻译表。

## 10. 非功能性需求

- **稳定性**：内存安全由编译器保证；渲染/分析任务异常不影响主进程（任务隔离）。
- **可移植性**：Windows / Linux / macOS；单一静态可执行文件（Windows 无运行时依赖）。
- **安全性**：不内置遥测；文件解析对畸形数据 fail-safe（拒绝而非崩溃）。
- **可维护性**：clippy 零警告为 CI 门禁；模块边界清晰，文档覆盖率目标 80%。
- **许可**：MIT / Apache-2.0 双协议。

## 12.2 v0.2.1 交付物与验收

1. **投影 / 坐标系识别**（导入时，`src/geo/mod.rs`）：
   - GeoJSON（`.geojson` / `.json`）：按 RFC 7946 默认为 WGS 84 经纬度
     （地理坐标系，EPSG:4326）；不读取非标准 `crs` 成员；
   - Shapefile（`.shp`）：读取同目录 `.prj`（WKT 文本）——识别投影模型
     （`PROJCS`/`PROJCTP` → 投影坐标系；`GEOGCS`/`GEOGTRP` → 地理坐标系）、
     EPSG 代码（取**括号嵌套最浅**的 `AUTHORITY["EPSG","<n>"]` 声明，
     即数据坐标系自身，而非内嵌基准地理系的代码）、WKT 首行元素名兜底；
   - `.prj` 缺失或无法识别时按"未知 / 未识别"处理，**不视为导入错误**
     （几何仍可渲染）；图层自身携带 `projection` 字段。
2. **工程默认投影 / 坐标系**（产品需求）：工程未设置投影 / 坐标系、且
   **尚无任何图层**时，导入的**第一个**图层的投影 / 坐标系成为工程默认值
   （判定在图层加入前；源数据无法识别投影的图层不占用默认值，留给下一个
   可识别的图层）。
3. **状态栏动态显示**：第三段实时显示 `投影: … | 坐标系: … | RustGIS <版本>`
   （未设置 → "未设置"；坐标系未识别 → "未识别"）；三语文案（zh/en/ja）
   随语言切换即时生效。
4. **工程文件 v3**（`.rustgis`）：工程级 `projection` 与图层级 `projection`
   字段持久化（序列化值与界面语言无关：模型为枚举字符串、坐标系为
   `EPSG:<code>` / 名称 / 空串）；**向后兼容** v1/v2 文件（缺省 = 未设置）；
   打开工程恢复工程默认投影，新建工程清回未设置，保存时落盘。

**已知边界**：只识别与展示，**不做坐标重投影**——混合坐标系的多个图层
按各自世界坐标直接叠加绘制，套合正确性依赖 proj 集成（§13）。

5. **质量门**：`cargo clippy --all-targets` 零警告（预存的 `LayerNode`
   枚举大小差异警告除外，属 v0.2 既有结构）；单元测试 69 项（65 过 + 4
   诊断基准忽略），新增 `.prj` WKT 解析（地理 / 投影 / 名称兜底 / 未知）、
   工程文件 v3 投影往返（工程级 + 图层级）、v1 旧文件兼容、首图层定默认
   （空工程采纳 / 无法识别不占用 / 后续图层不改默认）三场景、状态栏三语覆盖。

## 12.3 v0.2.2 交付物与验收（已完成）

1. **缓冲区分析对话框**（`src/app/buffer_dialog.rs`，对标 ArcGIS「Buffer」工具）：
   **独立顶层窗口**——经 egui 多视口（viewport / `show_viewport_deferred`）由 winit
   创建**真正的系统窗口**，不是主窗口内的内嵌面板：拥有自己的标题栏、最小化 /
   最大化 / 关闭按钮与任务栏条目，可与主窗口并列摆放、互不遮挡；关闭窗口（或
   `Esc` 之外的系统关闭）等同于「取消」。表单状态存在 `Arc<Mutex<…>>` 共享单元里，
   窗口界面只发「消息」（确定 / 取消 / 添加图层 / 占位提示）回主线程，主线程每帧
   刷新图层列表与三语字符串——因此对话框开着时主窗口仍可平移缩放地图。
   该窗口骨架同时服务「地理处理」菜单里的 5 个叠加工具（见本节第 9 条，
   `src/app/geoprocess_dialog.rs`），两者共用同一套布局与消息约定。
   输入要素（图层下拉 + 文件夹按钮＝从文件添加图层）、输出要素类（文本框 +
   保存对话框，默认 `{输入图层名}_Buffer.geojson`）、距离 [值或字段]（线性单位
   数值 / 输入图层字段，含米·千米·英尺·英里·码·海里·度）、侧类型（FULL / LEFT /
   RIGHT / OUTSIDE_ONLY）、末端类型（ROUND / FLAT / SQUARE）、融合类型
   （NONE / ALL / LIST）、融合字段（复选框列表 + 全选 / 取消全选；「添加字段」
   按 ArcGIS 语义禁用——该按钮仅在 ModelBuilder 中可用）；右侧**上下文帮助
   面板**随鼠标悬停的参数切换说明（NONE / ALL / LIST 等），底部按钮为
   确定 / 取消 / 环境... / 隐藏帮助 / 工具帮助；环境设置与工具帮助为占位。
   距离输入**非零数值**即可（负值 = 侵蚀，与 ArcGIS 一致）；融合类型选 LIST
   时必须至少勾选一个融合字段，否则确定前即报错。
2. **缓冲区引擎**（`src/geo/buffer.rs`，几何运算委托 **`geo` 0.33**，纯 Rust）：
   在「缓冲距离 = 1」的归一化空间里调用 `geo::Buffer`（底层 i_overlay 的
   stroke / outline），再用各向异性仿射缩放回世界坐标——投影坐标系为等向缩放
   （欧氏缓冲）；**地理坐标系 + 线性单位**按分组中心纬度取
   `dx = 1/(111320·cosφ)`、`dy = 1/110540`，即近似测地线（GEODESIC）缓冲。
   圆弧与圆角由 `LineCap::Round(π/16)` / `LineJoin::Round(π/16)` 提供（每象限
   8 段、整圆 32 边形，同 ArcGIS 默认）。归一化**按融合分组各自进行**（原点是
   该组包围盒中心、参考距离是组内平均 |距离|），并对缩放因子设跨度下限
   （归一化坐标压在千级），因此「小缓冲 + 大跨度」的数据（如全国点集上的
   100 米缓冲）不会因底层布尔引擎的相对容差被放大到要素尺寸而丢失结果。
   点 = 圆；线 = 双侧体育场（ROUND 半圆端 / FLAT 平端 / SQUARE 方端外延）或
   单侧（LEFT / RIGHT = 完整缓冲 ∩ 该侧半平面并集）；面 = 外环外扩 + 孔内缩，
   OUTSIDE_ONLY 用 `BooleanOps::difference` 把输入面自身挖成孔；
   **负距离 = 侵蚀**（内缩，ArcGIS 语义一致）。
3. **融合与布尔运算**（`geo::unary_union` / `geo::BooleanOps`）：NONE 每要素
   独立成环；ALL 全部求并（消除重叠）；LIST 先按融合字段取值组合分组、组内求并，
   组间保持独立要素。`unary_union` 按环方向自动选填充规则，因此进并集前统一
   `orient(Direction::Default)`（外环 CCW / 孔 CW）；归并**每次最多 128 个形状**，
   并在碎片重叠度极高（总面积 ÷ 外接框面积 > 32）时切换为两两归并（实测依据见
   本节「性能」条）。
4. **孔感知三角剖分**（`src/geo/tri.rs`，封装 `geo::TriangulateEarcut`）：
   外环与孔一起送 Earcut，输出三角形总面积 = 外环面积 − 孔面积（此前孔只能
   描边、不能填充，缓冲区结果因此无法正确显示空心区域）；顶点规模超过
   1 万时按环切块多线程，结果顺序与串行一致。
5. **图层属性采集与持久化**：`Layer` 新增 `fields` / `attrs` 与几何→属性行号

   「地理处理」下 6 项——**缓冲区…**（复用上面那条缓冲区窗口）与**裁剪 / 相交 /
   联合 / 合并 / 融合**（5 个工具共用同一个窗口骨架，只是参数不同）。窗口布局与
   缓冲区一致：输入要素列表（多选，勾选顺序＝叠加顺序）、输出要素类（默认
   `{主输入名}_{工具后缀}.geojson`）、融合字段（仅「融合」显示，复选框 + 全选 /
   取消全选）、右侧上下文帮助（**工具**一行随工具切换，说明该工具的语义与输入

     拆成新折线）；**点**保留落在裁剪面内的；属性全部来自输入图层。
   - **相交**：计算所有输入的公共部分，要求输入同属**点 / 线 / 面**一类（跨类型
     直接报错并指出是哪个图层）。面＝逐对布尔求交（先按包围盒预筛，避免 O(n·m)
     的无效调用）；线＝输出**交点**（共线重叠段不拆分，见「已知边界」）；
     点＝所有输入都覆盖的位置。属性为各输入字段的**并集**，重名字段按 ArcGIS
     习惯加 `_1`、`_2` 后缀。
   - **联合**：把多个面图层的并集切成**互不重叠**的要素——按输入顺序逐个
     「先到先得」：每个要素先减去已被覆盖的部分（`difference`），再并入覆盖集合
     （`oriented(unary_union(...))`），因此重叠区域的面积只归属最先覆盖它的那个
     图层，不会重复计入。只支持面（点 / 线请用合并）。
   - **合并**：纯拼接，不做任何几何运算——重叠保留两份，属性列取并集并补齐空值。
   - **融合**：按融合字段取值分组（组内面用 `unary_union` 归并），输出要素只保留
     这些融合字段；不勾选任何字段＝「融合全部」，得到一条整层并集。
   - 与缓冲区共用同一套几何约定：坐标先平移到包围盒中心、等比缩放到千级跨度再
     做布尔运算（`Frame`），结果按原比例还原并设置高亮样式（每个工具一种强调色）；
     字段合并、去重与输出命名都在引擎侧完成，写盘交给
     `buffer::write_geojson`（本版起按要素输出 `properties`，属性随结果落盘）。

**已知边界 / 与 ArcGIS 的差异**：不提供「方法（Method）」与「环境设置」参数，
PLANAR / GEODESIC 由坐标系 + 单位自动判定（地理坐标系 + 线性单位 → 近似测地线，
精度为球面近似，非椭球积分）；单侧缓冲（LEFT / RIGHT）用「完整缓冲 ∩ 半平面
并集」实现，凹侧同样自动取圆弧连接；融合字段列表不含 FID；GeoJSON 属性字段按
**字典序**排列（`serde_json` 未启用 `preserve_order`，Shapefile 严格按 `.dbf`
列序）；仍不做坐标重投影（§12.2 边界不变），混合坐标系图层按各自世界坐标直接
运算；输出为 GeoJSON 文件而非地理数据库要素类；`add_field`（添加字段）按钮禁用；
融合的归并策略是**自适应**的——碎片总面积远大于外接框面积（重叠度 > 32）时判定
为「大量近乎重合的碎片」，改用两两归并，否则每批 128 个一次 `unary_union`
（底层 i_overlay 在「大量几乎重合的输入」上会严重退化：100 个圆心相距 1e-4
的圆一次归并需 117 s，两两归并只需 29 ms；而 5000 个正常散布的点一次归并
140 ms，两两归并要 1.47 s）。

叠加分析（第 9 条）额外的差异与边界：**线段求交**只输出交叉点，共线重叠段不
拆分（ArcGIS 会返回重叠线）；**联合 / 融合的输出不做多部件要素**——同一属性的
多个不相连面会拆成多行（本版一行 = 一个面，与「点/线/面各成要素」的存储模型
一致）；融合**不提供统计字段**（FIRST / SUM / MEAN 等），只保留融合字段本身；
相交的**输入顺序**决定属性列顺序与主输入（决定字段列表、默认输出名）；叠加工具
一次只能处理**同一几何类型**的输入，混合类型的输入会被明确拒绝而不是静默丢弃。

> 实现说明：v0.2.2 草案曾自研平面排列布尔引擎与 ear-clipping 剖分

**目标**：允许向工程添加栅格图层，首先支持 TIF / GeoTIFF 的打开与浏览（对标

   ModelTiepoint → GCP；坐标系取 GeoKeyDirectory（3072 投影 / 2048 地理）、

## 12.5 v0.4 Sentinel-2 SAFE 支持交付物与验收（当前版本）

**目标**：在既有栅格框架上支持 Sentinel-2 的 `.SAFE` 产品包（L1C / L2A），
无需解压内部 JPEG 2000 波段，直接按需解码视窗像素浏览（对标 ArcGIS Pro /
QGIS 打开 SAFE 后的多波段栅格行为）。

**设计取舍**：`wbraster` 一类实现的 `sentinel2_safe` 只做**包级发现与元数据
解析**，像素解码委托给 JPEG 2000 解码器；本项目沿用同一分层——`safe.rs` 负责
目录结构、`MTD_TL.xml` 地理编码与波段文件枚举，`jp2.rs` 负责解码。解码器选
**`j2k` 0.12**（frame-sg 的纯 Rust 实现，依赖 `j2k-core` / `j2k-native` /
`j2k-types` / `moxcms`），不引入 OpenJPEG 的 C 绑定，保持「纯 Rust、无 C 依赖」。

1. **包识别与发现**（`src/raster/safe.rs`）：`is_safe_package` 接受 `.SAFE`
   目录、含 `MTD_MSIL*.xml` 或 `GRANULE/` 的目录、以及 `MTD_MSIL*.xml` 文件
   本身；产品级别优先看目录名（`MSIL1C` / `MSIL2A`），其次 `PRODUCT_TYPE`；
   顺带抽取 `SPACECRAFT_NAME`、`DATATAKE_SENSING_START`、`PROCESSING_BASELINE`、
   `TILE_ID` 等元数据项展示在「图层属性 → 源」。
2. **地理参考**：读 `GRANULE/<…>/MTD_TL.xml` 的 `Geoposition`
   （`ULX` / `ULY` / `XDIM` / `YDIM`）与 `Size`（`NROWS` / `NCOLS`），
   `HORIZONTAL_CS_CODE`（`EPSG:32633` 形式）解析成 EPSG 代码，
   `HORIZONTAL_CS_NAME` 作为名称兜底；仿射变换 `a=xdim, b=0, c=ulx,
   d=0, e=-ydim, f=uly`。缺地理编码时**不崩溃**，按像素坐标显示并标注来源。
3. **波段枚举**：扫描 `IMG_DATA/R10m|R20m|R60m`（旧式布局兜底 `IMG_DATA`
   直下），按文件名识别 `B01`–`B12` / `B8A` / `TCI` / `SCL` / `AOT` / `WVP` /
   `PRD` / `PVI` / `MSK_*`；排序为 TCI → B04 → B03 → B02 → B08 → 红边
   （B05/B06/B07）→ 短波红外（B11/B12）→ B01/B09/B10 → 场景分类 / 气溶胶 /
   水汽 / 云概率 → 掩膜 → 其它；波段名带中文说明（`B04 红`、`B8A 窄近红外`、
   `TCI 真彩色`、`MSK_QUALIT`…）。三分量 TCI 拆成红 / 绿 / 蓝三个显示波段，
   各自指向同一码流的不同分量。**同名波段在 `R10m` / `R20m` / `R60m` 各有一份
   独立副本，只保留分辨率最高的那一份**（`rank_and_dedupe`）：真实 L2A 产品的
   `IMG_DATA` 有 42 个 `.jp2`，去重后是 18 个波段。
4. **多分辨率网格**：SAFE 的 10 / 20 / 60 m 目录映射成「虚拟层级」
   （1 / 2 / 4 … / 32 倍缩小，`LevelSource::Safe`）；虚拟层级不占存储，往深处
   多铺几级只有好处——全幅缩略显示时直接取 1/16、1/32 的窗口，解码像素少一个
   数量级（真实 L2A 的全幅 fit 视图解码量从 1373² 降到 687²，耗时 1.9 s → 0.8 s）。
   `read_safe_plane` 按波段自身分辨率换算源窗口（10 / 20 / 60 m → 相对因子
   1 / 2 / 6），把 20 m、60 m 波段最近邻重采样到请求窗口，因此**任何波段都能在
   同一张地图里对齐显示**。
5. **JPEG 2000 解码**（`src/raster/jp2.rs`）：码流按文件缓存（LRU 6 份，10 m
   波段单文件 20–30 MB，足够覆盖一次 RGB 合成 + 若干低分辨率波段）；解码走
   **分量平面**接口（`decode_native_region_components` /
   `decode_native_components_at_reduction`），而不用 `j2k` 的打包像素格式——
   后者只接受 `Gray` / `RGB` 色彩空间，ICC 标记过或 4 分量码流会被拒绝
   （`backend color space cannot be mapped to requested N-bit pixel format`）。
   区域足够大时改用「整幅降采样」层（小波分辨率 1/2、1/4 … 1/256），小区域则
   只解全分辨率的请求区域，两者取解码量更小的一个；降采样层不可用（超出码流
   分辨率阶梯）时自动退回全分辨率区域解码，正确性优先。**全分辨率区域解码按
   64 MiB 条带切分**（`MAX_STRIP_BYTES`，带宽 × 分量数 × 2 字节计），每条带
   重建解码器上下文：`j2k` 自己的「常驻分量」上限是 512 MB，而真实 L2A 的
   10 m 三分量波段整幅解码需要约 540 MB，一次性解会直接报
   `native decoder context retained components requires … exceeding the …-byte cap`。
6. **不构建金字塔**：`build_overviews` 对 SAFE 直接返回 0，且
   `internal_overviews` 置为虚拟层级数，导入时**不再弹出**「是否构建金字塔」。
7. **与既有栅格框架完全同构**：`DatasetSource::Tiff` / `DatasetSource::Safe`
   两种数据源共用 `RasterDataset` 的公开接口（元数据、窗口读取、
   `read_display_source`、统计、bounds），因此显示采样、拉伸 / RGB 合成、
   纹理缓存、图层属性六页签、工程文件持久化**零改动**复用。
8. **统计**：SAFE 元数据里没有 GDAL 统计字段，统计槽位按波段数预置，
   「计算统计」走与 GeoTIFF 相同的分块抽样累加器（后台线程 + 进度 + 可取消）。
   **超过 1600 万像素的影像改为整幅降采样统计**（`statistics_target`：长边压到
   2048，TIFF 走概览、SAFE 走小波分辨率），结果标记为「估算」；小影像仍按步长
   逐窗抽样。真实 L2A 的 10980² 全幅必须走这条路——逐窗全分辨率读会在第一个
   窗口就撞上解码器的内存上限，统计失败后拉伸拿不到 min/max，画面会发暗。
9. **UI 接入**：「插入」菜单新增「添加 Sentinel-2 SAFE 产品包...」（三语），
   用系统文件夹选择器选 `.SAFE` 目录，后台线程解析后自动加入图层并缩放至全图；
   Ctrl+O 风格的「添加栅格数据」也接受 SAFE 目录（`is_raster_path` 统一判定）。
10. **测试**（`src/raster/fixture_tests.rs` 第 13 节 + `src/raster/safe.rs`
    `mod tests` + `src/app/raster_op.rs`）：`safe.rs` 12 项单元测试覆盖波段识别
    （含 `B8A` / `MSK_*`）、排序、中文说明、命名空间化 `MTD_TL` 解析、产品级别
    判定、缺元数据 / 缺波段的报错、分辨率目录枚举；端到端测试用真实 JPEG 2000
    样例文件拼出 SAFE 树（`MTD_MSIL2A.xml` + `MTD_TL.xml` + `IMG_DATA/R10m`
    下的 `.jp2` 副本），断言波段数 / 压缩与分块布局 / 边界与 EPSG / 窗口读取 /
    统计 / 越界波段报错 / `build_overviews == 0` / 虚拟层级数，另有整幅缩到 8×8 的
    `read_display_source`（走深层小波降采样）与「导入 → 纹理上传 →
    图层属性不 panic」的无头端到端测试。
11. **质量门**：`cargo test --bin rustgis` 全绿（194 项，含 5 项历史基准忽略）；
    `cargo clippy --all-targets` 零警告；`cargo fmt --check` 通过；版本号 0.4.0。

**真实验收**：以欧空局下载的 `S2A_MSIL2A_20261016T101041_N0513_R022_T32TQR_…`
（10980²、EPSG:32632、42 个 `.jp2`）实测：打开后为 18 个波段、`U16 / 15 位`、
状态栏「统计完成：3 个波段」，默认 TCI 真彩色正常显示，缩放 / 平移无报错。

**已知边界**：只解析 `MTD_TL.xml` 的 `Tile_Geocoding`（不做 UTM → WGS84 重
投影，与 v0.2.1 起的「只识别不重投影」一致）；`MSK_*` 掩膜按普通波段显示；
光谱波段是 15 位，按 `U16` 处理（数据集级位深取所有波段的最大值，避免被 8 位
的 TCI 带偏）；大影像的统计值来自降采样、标记为「估算」；
JPEG 2000 解码目前单线程按窗口进行，未做瓦片级并行；码流整份读入内存

## 12.6 大型栅格异步渲染（本次交付）

**问题**：真实 L2A 产品（10980²、TCI 三分量）全幅显示时，绘制线程每帧都要在
**界面线程**同步解码一张纹理。实测（release）单次纹理重建：全幅缩略 3.5 s、
半幅平移 1.8 s、1:1 视窗 0.6–0.9 s。平移一旦超出 20% 外扩范围就触发一次重建，
画面因此「几乎没法动」。

**方案**（`src/raster/paint.rs` 重写，约 990 行）：

1. **绘制线程永不解码、永不等锁**。数据集元数据、地理参考、统计值统一抓成
   `DatasetSnapshot`（含 `statistics_version`），绘制只用快照；取快照走
   `RasterLayer::try_dataset()`（`try_lock`），后台统计 / 解码持锁期间直接沿用
   旧快照，一帧都不会被阻塞。
2. **异步构建纹理**。超过 400 万像素（`ASYNC_DECODE_PIXELS`）的图层把解码丢给
   后台线程（`spawn_build` → 自己的 `RasterDataset` + `build_texture` → 信道回传
   `BuiltTexture`），绘制线程 `try_recv` 取回后上传纹理；`display` 变化的结果
   直接丢弃。小影像仍走同步路径（毫秒级，保持零延迟）。
3. **全幅底图兜底**。大影像先请求一张长边 768 的底图（`BASE_CANVAS_SIDE`），
   底图单独合成一张缓存；细节纹理在交互过程中就异步请求，到货即覆盖。
   任务在跑时用 `request_repaint_after(40 ms)` 轮询，不忙等。
4. **SAFE 虚拟层级加深**（`open_safe` 由 1/2/4/8 扩到 1/2/4/…/32）：全幅缩略
   直接取深层窗口，解码像素少一个数量级——实测全幅 fit 视图 1.9 s → 0.8 s，
   490 px 缩略 1.9 s → 0.7 s。虚拟层级不占存储，加深无成本。
5. **缩放级别按非对称容差判定**（修复「放大一格就整幅变糊」）。旧规则是「密度
   差超过 25% 就整屏退回 768 px 底图」，而一次滚轮就是 1.6–2 倍缩放，于是每次
   放大都立刻掉回底图、还要等一次 0.7–1.8 s 的解码才恢复。参考 QGIS 的
   `maxOversampling` 语义改成非对称容差（`same_zoom`）：**放大方向**只有密度比
   超过 1.25 才重建（旧纹理用双线性拉伸，比底图清晰得多），**缩小方向**
   超过 1.75 才重建；同时删掉交互期的半分辨率降级（它会把手上更清晰的纹理换成
   更糊的一张，还要再等一次全分辨率）。一次滚轮现在完全不发起重建，画面立刻
   就是清楚的。
6. **放大交给纹理过滤**。块纹理的像素数不超过该块对应的源窗口像素数（`tile_size`）：
   放大时由 `TextureOptions::LINEAR` 双线性插值，避免把几十像素的窗口在 CPU 里
   重采样成几百像素的方块马赛克；缩小时仍在 CPU 侧重采样，保证缩小不丢细节。
   整块化重构见 §12.8。
7. **纹理尺寸变化时换新句柄**（修复缩放「花屏」的另一处来源）。缩放时每次重建的
   纹理尺寸都不同，原地 `TextureHandle::set` 会触发 egui 图集重新分配；这里改成
   「尺寸一致才原地更新，否则丢弃旧句柄、`load_texture` 新建」——同一尺寸的平移
   更新仍是零分配的原地上传。
8. **平移时旧纹理继续按世界位置滑动**（修复放大后平移「整屏变糊」）。上一张细节
   纹理即使不再完整覆盖视野也照常绘制——它只是没盖住新露出的边缘，边缘由底图
   先补，新的纹理到货后覆盖；只有「缩得太狠」（1 个纹理像素摊到 2 个以上屏幕
   像素，会混叠出横条）时才暂时不画。实测 10 倍放大下全程拖动，画面保持清晰、
   无整屏糊片。
9. **层级窗口坐标必须乘 `divisor`**（修复深度放大出现的整屏竖条纹）。SAFE 的
   细节纹理取自「虚拟层级」：`window` 是**层级像素**坐标，换算成基网格像素时
   起点和步长都要乘 `divisor(2^k)`。旧代码只给步长乘了、起点没乘，于是减去
   解码区域起点 `decoded_y0 = roi.y / denominator` 后整片变成负数，被
   `clamp(0, last)` 全夹到解码区的第 0 行，屏幕上就是整片竖条纹（实拍
   `roi=(636,3120,3104x2284)` 下 `y=[-2340,-58]`）。`level_shift == 0` 时
   `divisor == 1`，错误不可见，所以只在深度放大（层级 ≥ 2）时暴露。映射已抽成
   `source_index()` 并配单测 `level_window_offset_scales_with_divisor`。
   同时 `pick_level` 的层级容差从 1.5 放宽到 2.0（少解一级、像素少 4 倍），
   全幅窗口的细节解码 1.8 s → 0.6 s 量级。

**验收**（真实 L2A 包 + 模拟鼠标拖动 / 滚轮）：

- 拖动期间界面帧间隔 p50 6.6 ms、平均 23.5 ms（含 40 ms 轮询空闲帧），
  不再出现 0.6–3.5 s 的整段冻结；松手后细节纹理自动补齐。
- **放大一格验收**（用户报「一放大就从图 1 变成图 2」）：一次滚轮（实测 1.59 倍，
  `density` 16.53 → 10.36）后 0.4 s 与 1.6 s 的截图 `r1_early.png` / `r1_late.png`
  都是清晰的，诊断日志显示**根本没有发起重建**——旧的 664 px 纹理直接交给双线性
  双线性拉伸，观感与 fit 视图一致。
- **深度放大验收**：连滚 6 格（`density` 16.5 → 0.93，约 18 倍）后截图清晰，
  无竖条纹、无纯色（`target/z5_fixed.png`、`target/z9_fixed.png`）；修复前同一
  位置是整屏竖条纹或纯色块。
- 无头测试 `large_images_decode_in_the_background_and_get_a_base_canvas`
  （2048² GeoTIFF：首帧不产生细节纹理、后台完成底图后可绘制）、
  `large_images_are_detected_for_background_decoding`、
  `snapshot_is_stale_after_statistics_are_stored`、
  `tile_windows_cover_the_whole_image`、`tile_range_covers_every_touched_tile`、
  `tile_size_keeps_aspect_and_respects_limit`、`tile_step_scales_with_density`、
  `tiles_closest_to_view_center_come_first`、
  `stale_tiles_are_dropped_only_when_too_coarse`、
  `level_window_offset_scales_with_divisor`（层级坐标换算，见第 9 条）。
  合计 `cargo test --bin rustgis` = 198 passed / 5 ignored。
- 放大后平移验收：10 倍放大下连续拖动 24 步（每步 12 px、间隔 70 ms），逐帧截图
  全程清晰、无整屏糊片、无横条；松手后自动换成全分辨率纹理。

**已知边界**：底图固定为长边 768，深度放大后拖动期间画面偏软（松手即清晰）；
细节解码仍单线程（每次一个任务），拖到新位置后需等一次解码（约 0.6–1 s）；
分块后不再有「整窗纹理上限」，CPU 合成的取舍与边界见 §12.9。

**「花屏」排查结论**：逐层排除了解码与合成——
① 真实 `TCI_10m.jp2` 的区域解码对比（同起点不同范围 / 不同起点相同重叠区、
5 组跨瓦片 ROI）逐像素 `max_diff` 全为 0；② 整幅降采样解码（÷4/÷8/÷16）的
平面按 10 个横向带统计「整行常量」，命中 0；③ 把每次构建出的 `ColorImage`
导出为 PPM 后统计同样的条纹特征，13 次构建全部干净。横向条纹因此出在「上传
纹理 / 绘制」这一层，对应上面第 5、7、8 条三处收紧。

**深度放大的竖条纹**（后续追加修复）：与上面不同，这类条纹是**数据**问题。
`RUSTGIS_NO_GPU=1` 关掉显卡路径后 CPU 同样有条纹，说明与 GL 无关；把送进
GPU 的平面 dump 成 PGM 后，肉眼可见「顶部一片竖条纹 + 下方完好影像」的水平
分界；再打印解码映射，发现所有行的源行号都是负数（`y=[-2340,-58]`），
`clamp` 后全部取第 0 行。根因就是第 9 条漏乘 `divisor`。修复后同一场景
`y=[1,207]`，5 格 / 9 格放大的截图都干净。

## 12.7 显卡 RGB 合成（历史方案，已由 §12.9 取代）

> **被取代**：本节的 `src/raster/gpu.rs` 与 `egui_glow` 依赖已删除，合成回到 CPU。
> 原因见 §12.9（与 QGIS 一致、去掉 GL 前提、可无头测试）。下文保留作为设计记录。

**问题**：v0.4 起大影像的解码已经搬到后台，但「波段 → RGB」这一趟仍在 CPU 上：
每个屏幕像素要做最近邻取样 + 三通道拉伸 / Gamma + NoData 判断，1296×839 的视窗
就是一百万次逐像素运算，缩放 / 平移时每次重建纹理都要再算一遍。

**方案**（新增 `src/raster/gpu.rs`，`paint.rs` 双路径；**已移除**）：

1. **CPU 只解码平面**。`build_planes` 调既有 `RasterDataset::read_display_source`
   拿到视窗内的原始样本平面（`Vec<f32>`，按显示通道去重），不做任何颜色映射；
   取样波段、通道下标、Alpha 波段由 `plan_bands` / `sample_plan` 与 CPU 路径共用。
2. **单波段一条 `R32F` 贴图**。`upload_planes` 按贴图生成号（`TexPayload.generation`）
   判断是否需要重传，`LINEAR` + `CLAMP_TO_EDGE` + `UNPACK_ALIGNMENT=4`，保留原始
   数值（不预乘、不量化），拉伸在着色器里做，换量程只需改 uniform。
3. **GLSL 复刻 CPU 语义**。片元着色器逐通道做
   `(v - low) / span` → 反相 → `pow(t, 1/gamma)`，任一分量是 NoData 时按
   「背景值」或「透明」处理，输出预乘 alpha（`vec4(rgb * a, a)`），与 CPU 路径
   逐条对齐。
4. **画进 egui 的绘制列表**。用 `egui_glow::CallbackFn` 注册 `PaintCallback`：
   egui_glow 在调用前已把 GL 视口设成回调矩形、调用后恢复自身状态，因此回调里只要
   铺满 NDC ±1 的四边形（顶点里把 v 翻转，匹配自上而下的行序），裁剪跟随 egui 的
   裁剪矩形，与矢量图层共用同一条渲染队列、叠放顺序自然正确。
5. **没有 GL 时自动退回 CPU**。`RasterPainter::with_gpu(bool)` 由 `main.rs` 用
   `CreationContext.gl.is_some()` 决定；无头测试与将来的 wgpu 后端仍走
   `build_image`，行为不变、无需双份测试。
6. **块尺寸与横纵比**。块边长按**屏幕像素**取固定值（`TILE_SIDE=512`），源像素
   步长 `step = round(TILE_SIDE × density)` 横纵同值，因此每一块在屏幕上永远是
   正方形：不会出现「宽窗口只有宽度被压、高度保持」导致的圆变椭圆。撞上限时由
   `tile_size` 对单块做**统一收缩系数**，仍然不破坏比例。

**验收**：

- 真实 L2A 包（10980²、TCI 三分量）全幅显示：颜色与 CPU 路径一致、朝向正确
  （无上下翻转）、NoData 与背景值处理一致，状态栏「统计完成：3 个波段」、
  「坐标系: EPSG:32632」。
- 滚轮放大 8 格：画面由显卡双线性插值，长条地块边缘平滑、无方块马赛克。
- 宽窗口（1400×900）放大 8 格 + 拖动：画面横纵比正确（不再出现圆变椭圆）、
  无整屏糊片，`target/t0_fit.png`、`t5_pan.png`、`z8_b.png`。
- 无头测试仍全绿：201 passed / 5 ignored（新增
  `quad_covers_the_whole_viewport`、`quad_flips_the_glyph_axis`、
  `plane_set_keeps_channel_indices` 三个几何 / 通道映射单测；GPU 路径本身依赖
  GL 上下文，由手工截图验收）。
- `cargo clippy --all-targets` 零警告、`cargo fmt --check` 通过、
  `cargo build --release` 通过。

**已知边界**：着色器按 `#version 140`（桌面）/ `#version 300 es` 生成；`R32F` 的
双线性过滤依赖驱动支持浮点纹理线性过滤（本机已验证；若某驱动不支持会退化为
最近邻观感）。透明合成按预乘 alpha 输出，与 egui 的混合模式一致。

## 12.8 分块栅格渲染（本次交付）

**问题**：§12.6 / §12.7 修完的三类缺陷（放大变糊、深度放大竖条纹、圆变椭圆）
根子是同一个设计选择——**整窗一张纹理**：纹理要覆盖整个视野，于是必须夹在上限
以内（挤压横纵比）、必须整张重建（一处失败全屏失败）、一块数据坏了整屏坏。
QGIS 不这么做：它按 `maximumTileSize()`（默认 2000 px）把请求切块，每块独立请求
分辨率、按整数设备坐标拼贴（`qgsrasteriterator.cpp:97-120`、
`qgsrasterdrawer.cpp:67-175`）。

**方案**（`src/raster/paint.rs` 重写主循环）：

1. **固定屏幕尺寸的块**。`TILE_SIDE=512`，源像素步长
   `step = round(TILE_SIDE × density)`；块坐标 `TileKey{level, col, row}`，
   `level` 只是网格代号。横纵用同一个 `step`，所以块在屏幕上恒为正方形。
2. **按视口收集 + 就近派活**。每帧遍历视口覆盖到的 `col/row` 范围，命中缓存只
   刷新 `frame`（淘汰用），缺的按「块中心到视口中心距离」排序派活；
   **每块解码线程自带一份 `RasterDataset`**（`RasterDataset::open` 实测 10–12 ms，
   远小于单块 0.1–0.6 s 的解码），因此 `MAX_TILE_JOBS=4` 是真并行——早期版本共用
   图层那把 `Mutex<RasterDataset>`，4 个线程只是排队，实际并行度恒为 1。单块完成后
   `request_repaint_after(30 ms)` 唤醒。实测 4 块 ×512² 全分辨率：串行 1.46 s、
   4 线程 0.83 s（约 1.8 倍；再高的并发被磁盘与解码器内部串行度限制）。
3. **新旧网格共存**。缩放跨过阈值时换新 `level`、新网格，旧块只要还没被缩到
   2 倍以上（`DRAW_MAX_DECIMATE`）就继续画——新块逐块盖上去，不会出现「整屏退回
   底图」的那一帧。放大方向不设上限：旧块再粗也比 768 px 底图清楚。
4. **一图层多张贴图**。块纹理按 `(图层, TileKey)` 缓存，每块一张 `TextureHandle`，
   被同 key 的新块替换时丢弃旧句柄；图层删除 / 显示设置变化时整层清空。
5. **底图仍单独合成**。底图（`BuildKind::Base`，长边 768）作为块还没到货时的兜底，
   与细节块共用同一套 `build_image`，不额外走特殊路径。
6. **淘汰**。缓存上限 `MAX_CACHED_TILES=24`，按 `frame` 最旧优先淘汰。

**验收**（真实 L2A 包，1400×900 窗口）：

- fit 视图：`target/t0_fit.png`，画面正确、无接缝。
- 一次滚轮后 2 s：`target/t2_notch_settled.png`，块已补到新网格，清晰无糊片。
- 8 倍放大（等比 1.6 连乘）等 6 s：`target/z8_b.png`，1:1 级别的地块 / 道路边缘
  锐利，**无竖条纹、无纯色块、无椭圆变形**。
- 拖动 240 px 松开：`target/t5_pan.png`，块随世界坐标平移，露出边缘由底图 +
  相邻块补齐，无整屏糊片。
- 门禁：`cargo test --bin rustgis` = 198 passed / 5 ignored、
  `cargo clippy --all-targets` 零警告、`cargo fmt --check` 通过、
  `cargo build --release` 通过。

**已知边界**：每块独立解码，深度放大后仍有「先出粗块、再逐块变清晰」的过程
（4 线程并行，单块约 0.2–0.6 s）；块是屏幕空间正方形，斜投影 / 非等比 CRS 下会
按屏幕像素而非地图单位对齐（当前只做单一投影，无影响）；块缓存 24 张 ≈ 768 px
级别的 24 块，深度放大 + 快速平移时会有重复解码。

## 12.9 CPU 合成（本次交付）

**问题**：§12.7 的显卡路径能省掉逐像素 CPU 循环，但代价是多一个 `egui_glow`
依赖与 GL 上下文前提、`R32F` 双线性过滤依赖驱动支持浮点纹理过滤、无头测试完全
覆盖不到（只能手工截图），也与 QGIS 的 `QgsRasterDrawer` + QPainter 路线不一致。
用户要求「渲染方式改为和 QGIS 一样（使用 CPU 渲染）」。

**方案**（删除 `src/raster/gpu.rs` 整个文件与 `egui_glow` 依赖）：

1. **合成回 CPU**。`build_texture` 统一走 `build_image`：按 `sample_plan` 选波段，
   逐像素取样 + 拉伸 / Gamma / NoData，产出 `ColorImage`（与 QGIS 在
   `QgsMultiBandColorRenderer::block()` 里做的是同一件事）。
2. **放大交给纹理过滤，且放大一律最近邻**。块纹理的像素数不超过该块对应的源窗口
   像素数（`tile_size` 的 `scale` 夹到 1.0），放大由纹理过滤完成——界面线程零成本，
   也不会把源像素在 CPU 里重采样成硬边方块。过滤方式与 QGIS / ArcGIS 的默认重采样
   一致：**只要在放大（`density < NEAREST_BELOW_DENSITY = 1.0`，即 1 个源像素铺到
   多于 1 个屏幕像素）就用最近邻**，只有缩小方向才用双线性（像素被合并时要平滑，
   避免锯齿与摩尔纹）。早期只在"放大超过 2 倍"时才切最近邻，于是 1–2 倍放大的区间
   里双线性把细节抹平，用户在不同窗口尺寸/缩放下会看到"有时糊有时清楚"——这正是
   用户反复报的"放大就模糊"。注意这与 `cached/density` 无关：判据只有 `density`。
3. **层级只按「每输出像素一个源像素」选，不再留 2 倍容差**（`pick_level`，
   `src/raster/mod.rs`）。早期为了少解码一级把容差放到 2 倍，层级又是 2 的幂，于是
   稳定挑到**比需要粗一级**的那层（缩放比 16.6 时挑 scale 32），纹理真实分辨率只有
   所需的一半——屏幕上任何缩放级别都是「插值放大过的糊图」，这就是用户报的
   「不管放大成什么层级都很模糊」。分块后每块只有约 512² 像素，多解一级很便宜，
   容差退回 1.001 倍（只吃掉浮点误差）。
4. **密度按物理像素算**。界面里的长度都是 egui 的「点」，而纹理像素要落在物理屏幕上：
   `density = 源窗口宽 / (屏幕宽 × pixels_per_point)`。Windows 缩放 125% / 150% 时
   若仍按点算，每块纹理都会被拉伸 1.25–2 倍，整幅图在所有缩放下都发虚。
5. **块缓存满了要先腾地方**（`make_room`）。派活前若 `tiles + pending` 已达
   `MAX_CACHED_TILES`（24），先按「最久未用」丢弃**不属于当前网格**的旧块。否则
   新网格的块永远派不出去，屏幕会停在几张旧的粗块上——表现为「有的地方清楚、有的
   地方一直是糊的」斑块（用户截图里那条斜向清晰/模糊分界就是这么来的）。
6. **分块仍是 CPU 合成的单元**。每块合成面积 ≤ 512×512（`TILE_SIDE`），一帧只合成
   视口需要的块；分块语义（§12.8）不依赖任何 GL 设施。
7. **删除只在 GPU 路径存在的东西**：`PlaneSet` / `DrawParams` / `ChannelParams`、
   `build_planes`、`RasterPainter::with_gpu`、`RUSTGIS_NO_GPU` 开关，以及
   `main.rs` 里 `cc.gl.is_some()` 的分支；绘制一律 `painter.image(...)`。
   净减约 700 行，`Cargo.toml` 少一个依赖。
8. **状态栏比例尺**（与 QGIS / ArcGIS 状态栏同一读法）：`1 屏幕像素 = 1 / (scale ×
   pixels_per_point)` 米，按 0.28 mm/像素折算成 `比例 1:xxxxx`，同时给出
   `1 像素 = x.xx m`。调试缩放/清晰度问题时，这个数字能直接区分"是不是还在缩小
   （density > 1）"和"已经进入放大（density < 1）"。

**验收**（真实 L2A 包，1400×900 窗口）：

- fit 视图 `target/cpu_fit_b.png`：颜色、朝向、NoData、状态栏与显卡版本一致。
- 4 倍放大 `target/v3_b.png`、8 倍放大 `target/cpu_z8v_b.png`、110 倍放大
  `target/v10_b.png`：全程**清晰**，无竖条纹、无纯色块、无椭圆变形；日志实测每块
  `win=506 → out=506 → level=506`（1 纹理像素 = 1 源像素），不再是 `8487 → 512 →
  266` 那种一半分辨率的糊图。
- 放大一律最近邻：8 倍放大（状态栏 `比例 1:13784  1 像素 = 3.86 m`）是硬边清晰
  的像素块（`target/n8.png`、`target/zz10_b.png`），不再是双线性的一片糊影。
- 分块渲染验收沿用 `target/t2_notch_settled.png`、`t5_pan.png`、`z8_b.png`；
  8 倍放大后再拖动 180 px（`target/patch_pan.png`）整屏均匀清晰，没有新旧网格混出
  的清晰/模糊斑块。
- 状态栏比例尺：小窗（1000×640）与最大化两种窗口下，同一缩放的读数一致
  （`8 倍放大 → 比例 1:13784  1 像素 = 3.86 m`）。
- 门禁：`cargo test --bin rustgis` = 200 passed / 5 ignored（比显卡版少 3 个随
  `gpu.rs` 删除的几何 / 通道映射单测，多 1 个 `make_room` 淘汰单测、2 个 `.ovr`
  构建单测）、`cargo clippy --all-targets` 零警告、`cargo fmt --check` 通过、
  `cargo build --release` 通过。
- `.ovr` 兼容性验收（2026-02）：4096×4096 RGB8 GeoTIFF 构建 4 级概览用时 0.52 s、
  文件 8.2 MiB；用 **GDAL 3.12.2**（rasterio 1.5.2 内置）复核
  `overviews(1) == [2, 4, 8, 16]`，逐级 `read(out_shape=…)` 成功且均值恒为 128.0
  （渐变理论值）；Pillow 复核 compression=5（LZW）、rowsperstrip=64、
  NewSubfileType=1；反向用 Pillow 生成的 `ext-gray.tif.ovr` 也被本程序读成
  外部概览（均值 128.54，理论 127.5）。

**已知边界**：放大超过源分辨率后不可能再有新细节（S2 是 10 m/px），所以放大后看到
的是尺寸放大后的像素块（与 QGIS 放大同一观感）；想看平滑插值可以缩小到
`density > 1` 的区间。CPU 合成成本随块数线性增长，深度放大 + 快速平移时仍由后台
线程逐块补齐（并发 4）。
